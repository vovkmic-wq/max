# Развёртывание и перенос на другую машину

Переносимость означает воспроизводимую установку на перечисленных поддерживаемых средах с сохранением редакционного состояния. Она не означает запуск на устройстве без нужной ОС, ресурсов, сети или разрешений платформ.

## Среды

| Среда | Цель поставки | Условие |
| --- | --- | --- |
| Windows x64 | Разработка и работа одного узла | Python venv, Node для установки OpenCode, PostgreSQL; либо Docker с Linux контейнерами и WSL2 |
| Linux x64 | Основной серверный профиль | Docker Compose либо проверенная native установка |
| Linux ARM64 | Расширение | Нужны соответствующие бинарники, образы и отдельный smoke тест |
| macOS | Расширение | Возможен container профиль после отдельной проверки |

Начальная оценка сервера для внешней LLM: 2 vCPU, 4 ГБ RAM и 20 ГБ свободного диска. Размер медиа и архива влияет на диск. Локальная LLM требует собственного расчёта памяти и производительности. Эти оценки проверяются нагрузкой NFR06.

## Состав пакета

Приложение, миграции, UI, lock файлы Python и Node, схемы, примеры, конфигурация OpenCode для принятой версии, scripts install/start/stop/backup/restore/doctor для поддерживаемых ОС, образы с digest, SBOM или перечень зависимостей и third party notices. Не включать реальные .env, токены, сессии аккаунтов, node_modules исходной машины и приватный контент.

На новой машине OpenCode устанавливается из зафиксированного пакета под её ОС и архитектуру. Версия 2.0.17 — исходная точка совместимости; изменение версии требует пересмотра API и permissions. Выбор Linux бинарника по Windows установке не проверяется копированием exe. Установочный скрипт не зависит от `C:\script\20260926-opencode`.

## Конфигурация

Корневой TOPIC.md и `config/sources.json` переносимы. app.json определяет относительные state, media и logs, профиль runtime и доступ к базе. Секреты поступают из secret store либо локального файла с ограниченными правами, отдельно от документов. `config/secrets.env.example` содержит только имена.

Для native режима OpenCode доступен через отдельный локальный процесс. Для Compose app и worker обращаются к runtime по внутреннему имени сервиса. Конфигурация адреса различается по профилю; localhost контейнера не является адресом другого контейнера. Конкретная команда запуска и адресная схема фиксируются после этапа совместимости, не переносятся из старых V1 инструкций.

## Установка

1. Проверить ОС, архитектуру, память, диск, права каталогов и доступ к принятому провайдеру и API.
2. Проверить хеш пакета, установить зависимости из lock файлов либо загрузить образы с digest.
3. Создать изолированные runtime state и data, настроить PostgreSQL и выполнить миграции.
4. Заполнить TOPIC.md и sources.json, передать секреты, проверить конфигурации через будущую команду doctor.
5. Запустить в dry_run. Проверить реальное создание текста через OpenCode и локальную цепочку.
6. Настроить канал, права бота и при необходимости публичный HTTPS endpoint webhook.
7. Пройти live smoke тест в отдельном тестовом канале, затем включить согласованный режим.

Эти шаги описывают требуемые будущие scripts; в текущем комплекте они ещё не реализованы.

## Работа webhook

Для production получения событий MAX требуется внешний HTTPS endpoint по правилам официальной документации; сведения о порте, TLS и секретном заголовке находятся в [INTEGRATION_FACTS.md](INTEGRATION_FACTS.md). На машине за NAT необходим доступный ingress или туннель к собственному серверу с HTTPS. Простая копия файлов этого не обеспечивает.

Если экземпляр только отправляет посты и использует разрешённое чтение API, публичный webhook не является условием одной исходящей операции. Любая включённая функция приёма событий требует настроенного ingress. Адрес подписки меняется при переносе и проверяется отдельно; нельзя одновременно запускать два потребителя одной доставки.

## Резервная копия

Согласованная копия включает dump базы, медиа, исходники доказательств по retention, активные конфигурации, manifests версий и хеши. Для согласования приостанавливать новые публикации и корректно завершать текущие записи либо использовать транзакционную копию БД с версионированными immutable blobs. Зафиксировать очередь, курсоры и unknown intents.

Копия данных шифруется. Секреты по умолчанию экспортируются отдельно через средство владельца; пароль шифрования не кладётся рядом с архивом. Restore сначала проверяет хеши и schema version. Перенос только конфигурации является клонированием настроек, а не восстановлением истории.

## Перенос

1. На старом узле поставить каналы на pause, остановить scheduler, завершить workers и зафиксировать intents с неизвестным исходом.
2. Сделать согласованную копию, записать migration manifest и остановить старый publisher. Только один узел имеет право отправки.
3. На новом узле установить принятые версии, восстановить БД и blobs в новый корень, повторно настроить секреты и права.
4. Проверить счётчики, хеши, историю, курсоры, бюджеты и неизвестные отправки. Новые задания первоначально запускаются в dry_run.
5. Обновить адрес webhook подписки и проверить доставку. Выполнить повторный сбор уже обработанных материалов: новых постов возникнуть не должно.
6. После live проверки возобновить режим. Старый узел оставить остановленным; возможность возврата требует передачи владения обратно.

## Обновление и откат

До обновления сохранять копию, затем проверить миграции на её восстановленном экземпляре. Если схема не совместима с прошлой версией, откат приложения включает restore базы и blobs согласованного момента. После восстановления не повторять неизвестные внешние отправки без сверки. Отчёт о переносе по AC19 является частью поставки.
