# Архитектурные решения и риски

Решения версии 1.0 определяют исходную реализацию. При изменении разработчик записывает дату, основание, альтернативу, затронутые требования и проверку.

## Принятые решения

| ID | Решение | Основание |
| --- | --- | --- |
| ADR01 | Отдельный проект, прежний OpenCode каталог только reference | Перенос и сохранение существующей работы |
| ADR02 | OpenCode runtime через изолированный адаптер принятой версии | Локальная версия V2 и изменяющийся experimental API |
| ADR03 | Python, FastAPI, PostgreSQL, постоянная очередь | Подходят для обработки материалов, панели и транзакционного состояния |
| ADR04 | Детерминированный publisher с outbox | Модель не должна определять разрешения и скрывать результат отправки |
| ADR05 | Создание канала через владельца до проверки официальной capability | Просмотренный публичный API не предлагает create_channel |
| ADR06 | Без обязательного векторного сервиса в первой версии | Уменьшение зависимости при переносе; смысловые кандидаты и OpenCode достаточны для проверки подхода |
| ADR07 | TOPIC.md со строгим JSON блоком и снимками | Удобное редактирование и воспроизводимая машинная валидация |
| ADR08 | Продвижение сначала plan_only, отдельные адаптеры исполнения | Реальная доступность площадки, разрешения и бюджеты различаются |
| ADR09 | Исходящая доставка допускает unknown | Нельзя вывести отсутствие публикации из потерянного ответа |

## Риски

ADR10, 6 октября 2026 года: добавлен SQLite профиль для автономного локального запуска на машине без Docker и PostgreSQL. SQLAlchemy модели сохраняют PostgreSQL профиль; live приёмка PostgreSQL проводится отдельно. В SQLite запускается один scheduler worker, тесты подтверждают атомарную выдачу заданий и резервирование бюджета. Для рабочего видео канала дополнительно добавлен импорт и публикация MP4 до 60 секунд; генератор видео остаётся отдельной неподключённой возможностью.

| Риск | Влияние | Предусмотренное решение |
| --- | --- | --- |
| API MAX меняется | Устаревший endpoint и SDK ломают доступ | Настраиваемый base URL, официальные факты, pin и контрактные тесты |
| OpenCode V1 и V2 различаются | Неверные permissions или клиент | Изолированный runtime, принятая схема и полный тест генерации |
| Источник недоступен боту | Нельзя собрать выбранный чужой канал | Capability probe, честный статус, другой разрешённый источник |
| Источники копируют друг друга | Повторы и ложное подтверждение | Кластеры событий и цепочка происхождения |
| LLM ошибается при переводе | Неверные цифры и факты | Alignment, проверки и review |
| Перезапуск после send | Повторная публикация | unknown и сверка до повторной отправки |
| Продвижение не окупается | Расход выше результата | Ограниченные эксперименты и фактическая экономика |
| Метрик нет в API | Неполный отчёт | unavailable и импорт с происхождением |
| Работа на двух перенесённых узлах | Двойная отправка | Передача владения, остановка прежнего publisher |
| GitHub проект не имеет понятной лицензии | Нельзя уверенно выбрать заимствование | Использовать наблюдения, код не копировать до разрешения и проверки |
| Сбор превышает диск и бюджет | Невозможность продолжать работу | Лимиты, retention, reservations и уведомления |

## Решения владельца перед live

Заполнить тему и аудиторию, выбрать пул доступных источников, определить тип и аккаунт канала MAX, подключить бота, выбрать провайдера и модель, задать реальные бюджеты и режимы. Для коммерческих размещений определить условия, ответственного и применимые требования. Для второй машины указать поддерживаемый профиль и способ доступа webhook.

Эти решения не нужны для подготовки документов и offline разработки. Незаполненные поля сохраняются явно, а не заменяются скрытыми предположениями агента.
